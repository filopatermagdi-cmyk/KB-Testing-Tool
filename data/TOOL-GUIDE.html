zilla-kb-tool — Complete Guide

Automated knowledge-base regression testing for Zilla voice agents • v2026-08-22

What it does. End-to-end pipeline that turns a Word-document knowledge base into realistic test questions (Arabic & English), speaks them to live Zilla voice agents through real calls or WebSockets, records the answers, and grades every answer with an LLM judge on Relevancy and Faithfulness - producing auditable score reports.
TypeScript (tsx)Python evaluator DeepEval 4.1.8Playwright call runner WebSocket runnerEdge TTS + ffmpeg Gemini question generatorGroq/OpenRouter/Ollama judges

2. Phase reference

Phase 1 extract-chunks — src/question-generator/extract_chunks.py

Parses the KB Word document into addressable chunks: one chunk per non-empty paragraph, one per table row (merged-cell duplicates removed). Tags each chunk with stable id (chunk_001…), language (ar/en by Unicode range) and group.

Inputspl_kb.docx
Outputdata/chunks.json - {id, type, text, language, group}
Servicesnone (local python-docx)

Phase 2 generate-questions — src/question-generator/generate.ts

Picks chunks (standalone + pairs from the same table for "combined" questions) and asks an LLM for one realistic customer question + ground-truth answer each, in EN and AR (same pair_id). Resumable, rate-limit-aware, saves after every question. Short chunks (<15 chars) skipped.

Input / Outputdata/chunks.json → data/questions.json ({id Q###, pair_id P###, language, question, expected_answer, source_chunks[]})
ServicesGemini gemini-3.6-flash or OpenAI-compatible (temperature 0.3, JSON mode)
Key envSAMPLE_SIZE (number|all), GENERATE_ENGLISH/ARABIC, RESUME, MAX_RETRIES, REQUEST_DELAY_MS

validate-questions re-checks any questions file (ids, uniqueness, languages, non-empty fields, source chunks resolvable against chunks.json). Console report only.

Phase 3 generate-audio — src/tts/generate_audio.ts

Speaks every question: Edge TTS (voices ar-EG-SalmaNeural / en-US-JennyNeural) → mp3 → ffmpeg → 16 kHz mono WAV; writes audio_file back into questions.json. Resumable, 3 retries.

Phase 4 build-sessions — src/session-builder/build_sessions.ts

Bundles questions that HAVE audio into multi-turn sessions per language using a seeded deterministic shuffle (mulberry32, seed RANDOM_SEED=42) so runs are reproducible.

Outputdata/sessions.json - {session_id S###_ar/_en, language, agent_id, messages[{turn, question_id, audio_file}…]}
Key envMESSAGES_PER_SESSION=10, TOTAL_SESSIONS_AR/EN=10, ALLOW_REPEAT_QUESTIONS, ZILLA_AGENT_ID_AR/EN

Phase 5 running sessions — two interchangeable runners

run-sessions.ts (UI mode)run-sessions-ws.ts (direct WS)
MechanismPlaywright browser drives the real Zilla web app, injects WAV clips as mic input (vendored CallRunner subprocess)One raw WebSocket to WS_URL .../audio/{token}; sends {"text": question}, assembles streamed reply sentences
NeedsZilla email/password login, staged clipsNo browser, no audio
Turn-complete logicCallRunner e2e heuristics1800 ms frame silence (settle) + 20 s hard timeout
OutputsIdentical shapes: per-session summary-<stamp>.json + aggregate data/runs/run-results-<stamp>.json
Scheduling envCONCURRENCY, CONCURRENT_AR/EN, --sessions S001_ar,... ; UI mode adds RESHUFFLE/SHUFFLE_SESSIONS/SESSIONS_PER_RUN

Phase 6 capture-answers — src/capture/capture_answers.ts

Joins raw run artifacts into the clean dataset the evaluator consumes: customer question → following agent answer, plus expected answer, source chunks, latency and call URL. Question order is taken from staged clip filenames (authoritative under reshuffle).

Inputnewest run-results-*.json (+ summaries, sessions, questions)
Outputdata/captured-answers-<ISO-stamp>.json with totals (sessions, answered/unanswered, avg latency) and per-turn records

Phase 7 evaluate — src/evaluator/evaluate.py

DeepEval-based grading of every captured answer:

  • Adapter OpenAICompatModel: plain chat-completions client so ANY OpenAI-compatible endpoint works - Groq cloud, OpenRouter cloud, or local Ollama. Temperature 0, key chosen by endpoint host. Counts tokens/calls per run.
  • Dialect-aware templates: wrappers adding our rules to DeepEval prompts: Levantine-dialect tolerance, Arabic-native comparison (no translation), English-only reasons, no-truncation claim extraction, "فقط" list-scope rule, natural-closings rule.
  • Metrics: Answer-Relevancy + Faithfulness (threshold 0.5); deterministic reasons rebuilt from raw verdict counts instead of LLM prose.
  • Resilience: auto-retry (3×) on HTTP 429, malformed JSON and empty completions; results saved after EVERY question so resume never loses work; result files are named per source AND per judge so switching judges never clobbers scores.
  • Observability: per-question judge latency + run-level token usage stored in output.

3. Sidecar tools

CommandWhat it does

6. Quality assurance of the judge itself

The judge was selected by grading the SAME 5 Arabic questions with three candidate models, then stress-tested with deliberately corrupted answers (poison test):

JudgeRelevancyFaithfulnessTime/5qVerdict
gpt-oss-120b (Groq)1.001.002.7 minadopted
nemotron-550b (OpenRouter)0.720.9010.1 minstrong but slow
qwen2.5:7b (local)0.620.57~3 minoffline fallback only
Poison test: 4/4 correct. Fake cities → Faithfulness 0.00; fabricated numbers (999) → Faithfulness 0.00; off-topic chatter → Relevancy 0.00; untouched control answer → perfect scores. Each metric catches exactly its own fault type.

7. Quickstart

npm install && pip install deepeval python-dotenv openai docx edge-tts
npm run agents -- --list          # pick agent ids -> .env
npm run extract-chunks && npm run generate-questions && npm run validate-questions
npm run generate-audio && npm run build-sessions
npm run run-sessions-ws           # or run-sessions for real browser calls
npm run capture-answers && npm run evaluate -- --sample 5 --no-resume
# or drive everything from: npm run ui
Quota cheat-sheet. Groq (judge): ~1,000 requests per rolling ~2h45m window - a 200-question run (~1,400 calls) needs two sittings or let retry+resume bridge the reset. OpenRouter free: ~50 requests/day total. Gemini (questions): standard free limits. Local Ollama: unlimited, lower accuracy on long-list comparisons.
